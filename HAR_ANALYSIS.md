## Phase 1 — Authentication & Session Flow

**⚠️ Important finding: the login request is NOT in this HAR.** The capture starts
mid-session — every request already carries a live JWT. This means the login
endpoint, its payload, and its response shape cannot be reverse-engineered from
this file. Nothing below about login is inferred/guessed — it's simply absent,
and the importer is built to take an already-issued session token as input
rather than pretending to know how it's minted.

What *is* fully visible in the HAR:

| Mechanism | Finding |
|---|---|
| Cookies | **None used.** Every request's `cookies` array is empty. |
| `Authorization` header | **Not present** on any request. |
| Actual auth mechanism | A JWT is appended as a **URL query parameter** `?session=<jwt>` on every API call (GET query string or appended to the POST URL). The frontend clearly stores this token (likely in memory or localStorage after login) and appends it to each request itself. |
| Token structure | Standard JWT: `header.payload.signature`, `alg: HS256`. Decoded payload: `{"data": "<opaque base64-ish encrypted blob>", "iat": 1784689200, "exp": 1784862000}`. The `data` field is itself encrypted/opaque server-side — it is **not** user info you can parse or forge client-side. |
| Token lifetime | `exp - iat` = 172,800 seconds = **48 hours**. |
| CSRF token | **None observed.** No `X-CSRF-Token`, `X-XSRF-Token`, or hidden form token anywhere. |
| `jibe-trace-id` header | A random UUIDv4, present on every call to `seaspan-j3.jibe.solutions/api/*` **except** the notification endpoints. Generated client-side per request purely for server-side tracing/logging — it is **not** a security token and can be freshly generated by the importer (`uuid.uuid4()`) with no consequence if omitted or reused. |
| CORS | `access-control-allow-credentials: true`, `access-control-allow-origin` echoes the calling origin exactly — confirms same-origin browser session context, not a public API. |

**Conclusion:** authentication is 100% session-token-in-query-string. There is no
CSRF protection and no cookie-based session to replicate — only the `session`
JWT needs to be carried on every request. **Because the login flow wasn't
captured, you must supply a valid `session` token to the importer yourself**
(log into the app, open DevTools → Network, copy the `session` value from any
API call's query string, or from wherever the frontend caches it). The
importer treats this as a config value and will clearly fail with an
"expired/invalid session" error (HTTP 401/403) if it's stale — at which point
you paste in a fresh one. **This is the one field this tool cannot self-serve**,
because the source data to derive it doesn't exist in the HAR.

Server-generated values in the response: `uid` (spare uid, new GUID),
`spareModelResult[].uid` (join-table row uid), `created_by` (from the session,
not sent by client), `date_of_creation`, `active_status`, `verification_status`.
Frontend/user-generated values: everything under `basic_information` /
`additional_information` in the request body, plus the resolved UIDs (maker,
criticality, unit_of_measurement, model) which the frontend looks up via the
GET calls above and substitutes before submit.

### Known gap (flagged per your instructions, not guessed)

`unit_of_measurement` and `material` are UIDs resolved from lookup tables that
**this HAR never calls**. The pattern for other lookups
(`/api/master/master/get_data?$table=j3_pms_lib_<x>`) strongly suggests a
table like `j3_pms_lib_unit_of_measurement` / `j3_pms_lib_material` exists,
but guessing the exact table name and shipping it would violate "do not
invent values." **The importer resolves these via a live lookup call at
runtime** using the same `get_data` pattern as criticality, and will tell you
immediately (and refuse to proceed) if that table name is wrong — see
`config.yaml` where you can correct the table name in one place if the
importer's first lookup call 404s.

## Phase 3 — CSV Bulk Import Format

The importer needs **human-typeable values** (part name, maker name,
criticality name, model name, unit name) — not raw UIDs — and resolves them
to UIDs itself via the lookup endpoints above, exactly like the web UI does.
This is the only CSV layout that requires no manual UID-hunting and is
"immediately usable" per the brief.
